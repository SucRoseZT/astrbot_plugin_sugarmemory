口径说明（看数字前先读）
    缓存命中率过低 · 疑难解答
    页面上有 两个数，优先看 记忆包命中率：本轮注入块 fp 与同会话上一轮一致的比例， 这是插件自己能保证的部分，frozen 架构下应接近 100%。整轮请求命中率 = 缓存输入 ÷（普通输入 + 缓存输入），包含框架 system + 历史 + 工具 schema + 记忆包； 它低不代表记忆包坏了，miss 常常出在外层的历史裁剪、工具集变化、provider 缓存 TTL。
    首轮、重载冷启动（日志会提示「本轮为重载冷启动」，这一轮 0% 是固定正常）、 自然过期（距上轮间隔超过阈值）都会单独打标，并从「有效命中率」里剔除，不算失败样本。 只有记忆包命中率低于 5% 且可比样本 ≥ 8 轮时，主页面才会出现这个入口。

    根据你库里的数据，优先查这几条
      完整排查清单（按命中概率排序）
      1 · 模型 / 中转是否支持并上报 prompt 缓存
      最常见的原因。框架只认 OpenAI 格式的 prompt_tokens_details.cached_tokens；不少国产模型、第三方中转 不返回这个字段，框架就恒记 0，此时 0% 是「没上报」而不是「缓存真失效」。另外有的 provider 是 整段/块级缓存，命中就报接近整段 prompt、不命中就直接 0，单轮只会看到 0% 和 99% 两个极端。
      怎么核对：看主页面「按 Provider」分组，若某个 provider 全 0、另一个有非零，基本就是上报口径；换一个已知支持缓存的模型（DeepSeek / OpenAI / Anthropic）发十几轮对照。
      2 · 新版架构是不是真的在跑
      inject_mode 要是 frozen，inject_enabled、token_stats_enabled 要开着。 改完代码必须重载插件 / 重启 AstrBot，还要让机器人真正聊几句才有新账单。 逐轮明细里 arch_ver 全是 dynamic 就说明进程里跑的还是旧版。
      怎么核对：明细一列都是 dynamic 标签，或「记忆包命中率」显示「不适用」；点右上角「查看之前的缓存命中率」可单独对照旧版 baseline。
      3 · 冻结轮数 / 节流时间太短，包被反复重建
      inject_freeze_seconds 秒或 inject_freeze_rounds 轮到点就会刷新流水、重建前缀。 而且插件节流常比 provider 的缓存寿命（常见 5 分钟~小时级）短得多，等于主动把还能用的前缀废掉。 L2 事实被改写会立即重建、好感跨阶段也会变。
      怎么核对：明细的「重建」列，以及「重建轮 vs 同 fp 连续轮」分组；重建轮占比高就把节流调大（例如 600 秒 / 30 轮）再观察，别在没数据时拍脑袋调。
      4 · 改配置 / 面板手滑导致所有分片一起失效
      前缀缓存是逐字节的：改了 pack_l2_limit、inject_budget_tokens、语气文案这类影响 prompt 的配置， 本来就应该全量重算一次，谁也省不掉。插件现在会把它记成 reason=config，一次性统一失效，不会各分片偷偷错开。 但改完别连着改好几次，每改一次就要重新写一轮缓存。
      怎么核对：「按注入块指纹 fp」的份数明显多于活跃会话数，说明一直在重建。
      5 · 预算设置有问题，触发了裁剪
      inject_budget_tokens 是上限，不是目标。设得比记忆包自然体积小会触发 trim_pack， L2 从十几条砍到 1 条，内容每轮抖、召回也跟着掉；插件日志会打 WARNING，面板「即时候选」里能看到 trim_notes。 调大预算不会多花 token（只要没超过包的自然体积），调小才危险。
      怎么核对：把预算调到 ≥ 包的自然体积（本库实测最重分片约 900 tok，1200 足够），低于 900 就会开始砍 L2。
      6 · 多会话 / 分片把 provider 缓存挤掉了
      常驻包按 (说话人, 会话) 分片，每片一份独立前缀。provider 侧能存多少块你控制不了， 活跃分片越多越容易互相挤掉；模拟里缓存容量只有 2 片时命中率会掉到六成左右。
      怎么核对：「按会话」分组，若会话多且普遍偏低，减少活跃分片比调 TTL 有效。不要把群聊的 who 降级成群 ID —— 那会把别人的记忆混进同一份包里。
      7 · 框架上下文策略每轮改写历史（整轮 0% 最常见的原因）
      「上下文管理策略」里的 max_turns 是请求发送前也要守的硬上限：历史超过它就按 overflow_strategy 处理一次。若 max_turns=12 且 trim_turns=1， 聊过 12 轮后每一轮都会丢掉最老一轮，整个 messages 前缀逐轮位移 —— 记忆包一个字节没变， 整轮命中率照样连续 0%。选 llm_compress 更糟：每次生成的摘要都不同，还额外多调一次 LLM。
      框架的「当前时间」注入挂在 user 消息尾部（extra_user_content_parts）， 不动 system 前缀，对前缀缓存无害，不用为了缓存关掉它。
      建议（你这套 frozen 常驻包 + 插件自带会话摘要的体系）：max_turns=-1 让历史只追加不按轮数裁剪、 overflow_strategy=truncate_by_turns、trim_turns=6~10（真溢出时一次丢一批，别每轮丢 1 条）、 fallback_max_tokens 按模型真实窗口设；prompt_prefix 保持纯 {{prompt}}，别塞动态变量。 改完聊 20~30 轮，对比「有效命中率」而不是单轮 0%/99%。
      8 · 其它插件往 system_prompt 追加了动态内容
      若有插件在 on_llm_request 里每轮往 req.system_prompt 塞会变的文本（状态、情绪、实时摘要）， 冻结也救不回来。注意插件目录 ≠ 启用列表：先看启动日志里的 disabled 名单，只排查真正启用的那几个。
      怎么核对：停用最近新装的插件试几轮；固定文本的注入（协议、指令）不影响缓存，只有每轮变化的才有问题。
      9 · 采样太少 / 一直在冷启动
      首轮、每次插件重载 / 重启后的第一轮、隔太久的那一轮都是写缓存，必然 0%。 现在这三类会在逐轮明细里打标（重载冷启动在日志里也会明说「本轮 0% 是固定正常」）， 并从「有效命中率」里剔除。工具循环里一次用户消息会打多次 LLM，插件只记「对话轮」， 和主库 provider_stats 不是 1:1，别跨表直接比。
      怎么核对：看「有效命中率」的加权值，而不是单轮 0%/99%；跑满 20~30 轮、让同一个会话连续聊，数字才有意义。

      01它是什么

      给聊天机器人补三样东西：记得住（分层记忆）、有亲疏（好感度）、知道人和人的关系（关系图）。

      数据全部落在本地一个 SQLite 文件里，不联网、不依赖向量库、不自带 embedding 模型。除了它自己触发的阶段总结，平时聊天不会多花你一次模型调用。

      三条设计取向，理解了这三条，后面所有行为都能推出来：

      • 能算的不用模型猜。检索、打分、裁剪、去重全是字符串运算和算术，不调模型。
      • 模型的输出只是草稿。总结返回的事实、关系，落库前要过门控和指纹去重，不合格就丢。
      • 注入量可数、可关。每轮塞进 prompt 的东西有 token 预算，超了按规则砍；每个模块都有独立开关。

      02三层记忆

      L3 原话每条消息一行
      保留天数可设
      会话摘要攒够一批才做
      把一长段压成几行
      L2 事实从摘要里抽
      带说话人和置信度

      L3 事件流：用户每发一条、AI 每回一条，各落一行，带说话人、会话 ID、到期时间。默认保留 14 天；到期后不直接扔——先压成一行主题词骨架再留一阵（见下面 08 节），设 0 就永久留着。

      会话摘要：同一个会话累计满 50 条用户消息（默认值，下面几个数字同理），再等 10 秒确认这轮聊完，就把最近 60 条用户消息 + 30 条 AI 回复拼起来，调一次模型，让它输出摘要 + 事实 + 关系。摘要也写在 l3_events 里，用 session_summary 标记。

      L2 事实：从摘要里抽出来的「谁 · 是什么」，例如「路人甲 · 女朋友 · 路人乙」。每条都有 speaker（谁说的）和 confidence（多确定）。

      怎么防重复：指纹 = sha256(subject|predicate) 取前 32 位。同一个指纹再次写进来，旧那条标成 replaced 并把 replaced_by 指向新那条，不删也不覆盖。所以面板里能点开一条记忆看它的修订链路，知道从哪句原话开始、中间改过几次。

      为什么非要分三层：原话太占地方但不能丢（要能追溯），摘要省地方但会糊（细节被模型吃掉），事实最省但会过时（关系会变）。三层各留一份，用的时候按预算取。

      03记忆包：每轮现拼，从不缓存

      每次你说话、在模型开口之前，插件现拼一段文字塞进 system_prompt，这段就叫记忆包。不写进对话历史，所以不会滚雪球。

      四步：

      • 取候选：当前说话人的有效 L2（默认最多 12 条）+ 相关 L3 原话（默认 5 条）+ 本会话摘要
      • 打分：把你的话和每条记忆都拆成相邻两字（2-gram），重合越多分越高；分数 = 重合数 × 2 + 置信度 + 稳定性 × 0.1。纯字符串运算，不调模型
      • 裁剪：超过预算（默认 600 token）就先砍 L3 原话，还超就砍低置信的 L2，直到塞得下
      • 渲染：拼成一段带标题的结构化文本写进系统提示

      作用域：默认按人隔离，只取当前说话人的事实和本会话的摘要。关掉这个开关会变成全库检索，别人聊过的东西会跑到你的对话里，面板调试时才建议关。

      用 2-gram 是因为它零成本、可解释、不会有假命中到离谱的程度。代价是不懂同义：你说「对象」，它翻箱倒柜也找不到「男朋友」那条。这个盲区后来靠召回三层补（见下面 07 节），但字面匹配本身还是这个脾气。

      04人物身份（AI 与人）

      一句话：一个人 = 一个 QQ + 一串称呼。好感、关系、记忆都记在「人」身上，不记在某个写法上。

      为什么要多这一层：同一个人的叫法太多——昵称、外号、英文名、甚至别人打错的名字。以前这些写法直接拿来当键，于是「用户丙」和「丙哥」在库里变成两个人，好感各记一半、关系图上两个点。

      • QQ 是身份锚：私聊时从会话串里自动认出 QQ 并绑上，面板里也能手动填。绑了以后换昵称、被叫外号都还是同一个人
      • 称呼表：每个称呼指向一个人。面板能加能删；删错不影响记忆，只是以后不认这个叫法
      • 自动学：你说「A 就是 B」「A 也叫 B」「B 是 A 的外号」时当场学下来（纯正则，不调模型），并且立刻把已经裂开的两个节点合回去
      • 只在有把握时自动合：写法相同（含看不见的占位字符）、QQ 相同、你亲口说过是同一个人——这三种才自动合。读音一样但字不同（王伟 / 王薇）只在面板上标「疑似同一个人」，点一下才合
      • 好感度：每人一个分数，你每说一条消息涨一次：4 × (1 - 当前分 / 上限)，最少 +1，越接近上限越慢，永远到不了顶。分数对上「阶段表」的阈值就是阶段，名字和阈值都能改
      • 影响语气：开着这个开关时，一句语气提示跟着关系快照一起注入。每个阶段可以在「好感阶段」里写自定义描述（写了就原样用）；没写就按阶段名里的关键词猜——名字里带「恋 / 爱 / 甜 / 暧昧」就提示亲昵宠溺，带「友」就熟络轻松，认不出就退回客气拘谨

      05人际关系

      一句话：这张表记的是「谁认为谁是什么」，不是事实库。

      每条边是「A 认为 B 是某某」。三个人各自说「路人甲是我男朋友」，就是三条互不覆盖的边。所以它会记下互相矛盾的说法，这是设计如此，不是 bug。人说谎、转述、开玩笑，只要是他自己讲的，都照记。

      • 证据：每条边可以挂多条原话，点开某人能看到这些原话
      • 快照注入：每轮只带当前说话人相关的边（默认 6 条），渲染成人话塞进系统提示，让 AI 知道该用什么口气
      • 工具：AI 可以调「记关系」（写）和「查关系」（读），两者都要过右边那六道闸
      • 重名归并：写之前先问「这个人是谁」——先查称呼表（丙哥 → 用户丙），认不出再看库里有没有同一个写法（只差括号备注、大小写、看不见的字符就算同一人，「张三」和「张三（群友）」合成一条）。都认不出才新建，并且立刻有身份记录，面板上就能给它绑 QQ

      06群聊策略：默认完全只读

      群里默认只做三件事：读记忆、答话、别的什么都不干。

      • 不写聊天记录，所以群聊内容一个字节都不入库
      • 不加好感度
      • 不计入总结条数，不会把私聊的总结节奏带偏
      • AI 不能改关系（开关默认关）
      这个插件没有做群聊适配，也不打算做。真要开，会遇到三个必现问题：说话人归属错乱（A 说的话被当成 B 的）、L2 互相串台、token 被群聊白白吃掉。开了之后出现的任何记忆错乱，都不算 bug。

      怎么判断在群里：三级兜底——先问适配器要群号，拿不到就看消息来源串里有没有群标记，还不行就看消息对象的类型名。因为不同适配器这三个来源不一定都给，只靠一个会把群聊当私聊处理。

      群不会出现在关系图和好感度里：见到一个群就把它的群号（和群名）记进 known_groups，读的时候凡是命中群号/群名、或者带 group: 前缀的，一律当群滤掉，不画节点、不算好感。历史数据会从存下来的会话串里反推群号补登记一遍。万一有人被误判成群，把那条群记录删掉即可，人或数据本身都没动。

      07召回三层：改个说法也能翻到

      上一节说过 2-gram 只认字面重合，网友实测下来最疼的就是这条：明明记过「20 岁」，你问「多大了」就是翻不到——改写过的问法十个里能召回的只有两三个。现在按「越便宜的越靠前」补了三层：

      • 第一层 概念归一（pack_query_expand，默认开）：一张手写映射表，把「多大了」「搞什么创作」这类口语问法先翻译成概念词（年龄 / 职业）再检索。零成本零延迟，代价是没进表的写法它管不了。
      • 第二层 问法别名（alias_autogen，默认开）：阶段总结时让模型给每条新事实顺手写几个「用户以后可能怎么问」的说法（「20 岁」→ 多大了 / 上大学没），存进库里的 ask_alias 列。检索时别名也参与打分，换个问法照样命中。存量旧事实会在之后的总结里分批补齐，不用手动动库。
      • 第三层 语义兜底（pack_semantic_fallback，默认关）：前两层全零命中时，调 Provider 的向量接口按语义相似度挑保底事实。兜的是「库里的写法和你的问法完全两个字」的极端情况（经典案例：「打字很响的设备」→「机械键盘」）。依赖模型支持 embedding，不支持时自动静默跳过，等于没开。
      顺序是刻意的：越靠前越便宜。绝大多数问法第一层就解决了，第二层管住「总结里记过的事」，第三层只收尾。三层全开时离线评测的改写召回从 20% 提到 90% 以上；第三层不支持的模型关掉它，前两层照常工作。

      08记忆生命周期：骨架与遗忘曲线

      以前的规则很糙：聊天原文存 14 天，一到期直接删——「半个月前聊过啥」从此无迹可寻。现在中间垫了一级，像人忘事一样，从关键句忘到只剩关键词：

      原话存 14 天
      完整可追溯
      骨架再存 90 天
      只余主题词
      消亡彻底删除
      不留残渣
      • 骨架 = 原话到期后压缩出的一行主题词索引（如「天气/通勤/咖啡」），零模型调用——纯字符串统计（2-3 字高频词）提取，不花一分钱。注入时标注「旧事骨架·只余关键词」，让 AI 知道这只是索引不是原文。
      • 防套娃：骨架再到期就彻底删，不会压第二次——关键索引的索引没有意义。
      • 提及率：长期事实的内容和你本轮说的话真的对上（字面命中事实本身、或语义钩子命中）才记一次 hit_count；只点到人名带出的整份档案、预算兜底硬塞的不算——计数反映「你聊到过什么」，不是「系统塞过什么」。频率的分母是入库到现在的天数，不是事实发生的天数，否则补录的半年前老聊天一进门就显示成 0 次/天。关着注入的时候也照常统计（影子模式不下线）。
      • 保留度决定沉底，不决定删除：长期事实按遗忘曲线算残留度 R = exp(-Δt / S)，Δt 是距上次被想起多久，S 由「确认过几次」和把握程度决定。面板上写「保留 62% · 约 40 天后沉底」。掉到 2% 且静默 90 天以上才归档——只改状态，数据一条不删，在「已沉底」里能捞回来。
      • 沉不下去的两类：身份、疾病、年龄、联系方式这些「人的底档」（自我相关 / 其他）只降权、永不自动归档；手动钉住的也一样。它们本来就不该每轮被提起，按热度淘汰等于把人的底档删了。
      • 每轮 12 条里有保底名额：底档类事实固定留最多 4 个位置，不会被「这轮聊的话题」全部挤出去——否则它们永远进不了包、永远没计数，最后被误判成没人要的东西。
      全部可关：l3_skeleton_enabled 关掉回到原行为（到期直接删）；skeleton_retention_days 改骨架寿命；inject_skeleton_limit 控制记忆包常驻几条骨架（默认 2，问「以前聊过啥」时至少有索引可查）。

      09推荐的配置顺序

      • 先别开注入。默认是影子模式：照常记录，AI 看不见。先跑几天，在面板里看记录得准不准
      • 觉得记得对，再开「注入记忆」。这时候 AI 才开始真的用上这些记忆
      • 只留一个记忆插件。装了别的同类插件就关掉这个的注入，否则同样的内容会注入两遍，白烧 token
      • 主人权限按需开。开了「只限主人」，就要确认你自己在管理员里，或者把自己的号填进额外授权名单，不然连你自己都会被挡
      • 总结专用模型可以挂个便宜的小模型。总结不追求质量，只追求把事记下来
      查这些东西分别是什么
      表结构、拦截规则、用量账、文件分工 —— 都不用背，用到的时候当手册查。

      01数据存在哪

      一个文件：data/plugin_data/astrbot_plugin_sugarmemory/memory.db。备份就是复制这个文件，换机器带走也是它。

      表存什么
      l3_events事件流。原始聊天（event_type=chat）、会话摘要（session_summary）和过期原文压出的骨架行（skeleton）都在这里，靠类型区分
      l2_facts长期事实：谁 · 什么属性 · 什么值 · 谁说的 · 置信度 · 指纹 · 问法别名（ask_alias）· 提及计数（hit_count）
      gate_audit门控审计：每条候选事实为什么被收下或被拒
      people一个人一行：规范名 + 绑定的 QQ
      person_alias称呼表：每个写法指向一个人（另存读音键，只用于「疑似同一人」提示）
      affinity每人一个好感度分（当前值 + 累计获得）
      affinity_stages阶段表：名字 + 阈值 + 语气描述，面板可改
      social_relations有向关系边：source 认为 target 是 relation
      relation_evidence关系原话证据，一条关系可以挂多条
      token_usage每次模型调用的账：模块、真实还是估算、输入 / 缓存 / 输出
      tool_idem幂等锁，工具写操作的指纹和时间戳
      circuit熔断状态，落库所以重载插件不会清零

      表是插件启动时 CREATE TABLE IF NOT EXISTS 自动建的，升级时只加列不删列，老库不会崩。

      02工具调用的几道闸

      写数据是唯一有破坏性的动作，所以从「AI 想写」到「真的写进去」之间排了六道闸，任何一道拒了都写不成。

      闸拦什么实现
      ① 开关整个工具不让用发请求前把工具从工具箱里摘掉，模型根本看不见它
      ② 身份谁能用平台管理员，或填进「额外授权名单」的号
      ③ 范围路人借 AI 改别人的关系非主人只能改「含他本人」的边，碰不到两个第三人之间的
      ④ 原话AI 被读到的文字骗想记的两个名字至少一个要出现在你这条消息里，否则软拒并让 AI 回头问你
      ⑤ 幂等模型重试写好多遍指纹 + 时间窗，重复的直接当成功返回，不再落库
      ⑥ 熔断一直失败还一直烧钱连续失败 3 次进 600 秒冷却（都可改），冷却完放一次探测，成功即恢复

      第 ④ 道是软拒绝：不报错，只回一句「这两人本轮没提到，先跟他确认」。AI 收到通常会回头追问一次，而不是把错误当成故障抛给你。

      第 ④ 道拦不住「你自己转述别人的话」——那种情况下两个名字都在你的原话里，属于你说的，照记。它只解决「AI 把读到的内容当成你授权的」。

      03Token 统计

      每次模型调用落一行账，记模块、来源、输入 / 缓存 / 输出三段。

      • 真实值：普通对话和阶段总结拿得到模型返回的用量，标 actual
      • 估算值：记忆包、关系快照不单独发请求，只能在拼装时按字数估，标 estimate
      • AI 主动调的工具（查记忆 / 翻外发历史 / 查关系）：工具本身不发请求，但它返回的文本会塞进下一轮对话的输入里真实消耗——按返回字数估一笔，标 estimate。调得越频繁这笔越大，嫌费就关掉对应工具开关
      • 缓存命中数看 provider：框架主要认 OpenAI 格式的 prompt_tokens_details.cached_tokens；有些 provider 把命中数放在别的字段（例如 DeepSeek 的顶层 prompt_cache_hit_tokens），框架没读时这一轮就会记成 0。所以「0」不一定是真没命中，也可能只是没上报

      面板里能看总量、24 小时、7 天、30 天，各模块占比，以及最近的逐条调用。子页「缓存命中率」把真实缓存输入按架构（frozen / dynamic）、provider、会话和注入块 fp 拆开，还能看逐轮明细；token_usage 新加了 arch_ver / inject_fp / rebuilt / freeze_rounds / cfg_ver / provider_id，旧数据在加列时统一锁成 dynamic 当 baseline。清空是两步确认，防止手滑。

      05已知限制

      • 群聊没有说话人归属，所以只读。这不是没做完，是不打算做
      • 记忆包只按人隔离。群里 A 提到 B 的事情，存下来挂在 B 名下，不会注入给 A
      • 拿不到缓存命中数，是框架层的解析问题，插件这边补不了
      • 字面匹配仍是地基：召回三层（概念归一 / 问法别名 / 语义兜底）补住了大部分改写盲区，但没进映射表的口语、还没补上别名的旧事实仍可能漏召回；语义兜底默认关，要 Provider 支持向量才有效
      • 总结是单次调用。返回的 JSON 解析失败会退避重试 3 次，三次都不行就跳过这一批，等下一批
      • 面板里没有弹窗。沙箱禁了系统的 alert / confirm，所以危险操作都是「点两次」确认

      06配置到底该在哪改

      有 两个入口，改的是同一个配置文件，但生效方式不一样，别弄混：

      入口生效说明写在哪
      本面板「设置 → 配置项」立刻，没有保存按钮每项下面都有一行白话解释
      AstrBot 官方插件配置页要保存 + 重载插件，只保存不重载跑的还是旧值也是白话解释，但分组按框架的方式展开

      建议一律在本面板里改，尤其是这几组：记忆、注入、总结、好感度、主人权限。原因很实际：在这里改完立刻生效，你可以马上发一句话看效果；在官方页改完要重载，重载前那段时间面板显示的是新值、插件用的还是旧值，很容易以为「改了没用」。

      官方那个配置页只当兜底用：插件没启动、面板打不开、或者你把「记录聊天」关错了导致面板没数据的时候，才去那边改。

      另外，官方配置页最顶上有条提示项（一项空字符串，叫「先读我」），它不参与任何逻辑，就是提醒你这件事，不用填、也不用管。
